# B06 — case map

Every case of package B06 (registry `cases.json` / `additional_scenarios.json`, gate G-DOMAIN) mapped to the tests that
demonstrate its expected outcome and to what a sealed check observes. Design: `docs/design/B06-domain-db-authz.md`. The
case-genuineness review of these tests (findings R24, R48–R54) is recorded in `docs/design/B06-review/F-case-genuineness.md`.

Status vocabulary (21 "Evidence classes"):

- **EXECUTED_LOCAL (integration)** — every named test exists under exactly that name and passed in the last `pnpm run verify`
  of the branch, each against a real PostgreSQL 17 cluster the test starts itself, and together the tests demonstrate the
  whole expected outcome of the case.
- **PARTIAL** — the named tests are EXECUTED_LOCAL (integration) for exactly the behaviour the row lists as demonstrated; the
  row names what is not demonstrated in B06 and the package and registry case that own it. A PARTIAL case is not claimed.

No case is PASS by being listed (reference/ACCEPTANCE_SCENARIOS "Execution record"); acceptance is the construction service's
independent review, and the execution record of 21 (subject, environment, input manifest, presealed expected truth, actual
public result, external effect identity, exit status, artifact digests, independent review) is assembled by that review, not
by this file.

Where the tests live, and why:

- **Command-level cases live in `apps/api/test/`.** They go through the real HTTP route (Fastify `inject`), the real
  composition root (`openDatabase` → `assembleApi`: the api's own verified pool on the temporary cluster, the `pg` unit of
  work, the shipped authorizer, admission limiter and handlers, the closed contract validator) and a real PostgreSQL 17. A
  command test that called a handler directly would not observe the admission order of manual 10, the problem translation,
  the authentication step or the answer's bytes, and `packages/persistence` may not depend on the api entrypoint
  (`architecture.rules.json`), so the earlier plan of `packages/persistence/test/commands/` was dropped. The fixture is
  `apps/api/test/support.ts`: the superuser oracle reads every table across tenants; hold points inside the unit of work
  (`journal.reserved`, `journal.commit`, `collaborator`, `after.commit`) fix interleavings deterministically, the second
  request being observed waiting on its lock in `pg_stat_activity` (a wait that never happens throws); no sleep synchronizes
  anything.
- **Structural and database-level evidence lives in `packages/persistence/test/`** (migrations, RLS, constraints, triggers,
  adapters, journals, leases, the last-owner race) **and `packages/application/test/`** (contracts, schemas, admission, the
  approval-hash golden vector). Database-level case tests drive the product's adapters (PgPlanRepository, PgCommandJournal,
  PgRequestJournal, PgLeaseStore) on real connections of the runtime roles; raw SQL appears only for the database facts beneath
  them.
- **Oracles are independent of the code under test** (21 "Independent oracles"): the approval hash is recomputed by a function
  written from reference/HASHING_AND_ACCOUNTING_RULES and pinned to a golden vector derived outside the product; row counts,
  states, events and journal rows are read by the superuser oracle. Every strengthened test was run against the mutation that
  had survived it (record file), and fails.
- What the acceptance tests bind that a deployment of this edition does not (I-INT-2): the plan-side ports ArtifactResolver,
  PlanPatchCompiler and DisclosureComposer (CMD023, CMD025), and for CMD026 an ExternalActionInspector that reports the
  completed stages a test registers. They are ports of `@kauro/application`, never fakes of the database.
