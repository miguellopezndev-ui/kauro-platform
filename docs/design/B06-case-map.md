# B06 — case map

Every case of package B06 (registry `cases.json` / `additional_scenarios.json`, gate G-DOMAIN) mapped to the tests that
demonstrate its expected outcome and to what a sealed check observes. Design: `docs/design/B06-domain-db-authz.md`. The
independent review of `b06/integration` at `e435a9a` (findings R1–R54) and its integration are recorded in design §12d; the
case-genuineness part of it (R24, R48–R54) in `docs/design/B06-review/F-case-genuineness.md`; the re-check of that
integration (re-check findings N1–N20 and the unconfirmed resolutions) in design §12d.5. The state/command/event matrix, the
error catalogue of every served route and the manual-10 contract-test applicability record are generated in
`docs/design/B06-state-command-event-matrix.md` (`tools/matrix.mjs`, checked by `pnpm run verify`).

Status vocabulary (every claim names its evidence class, 21 "Evidence classes"; PARTIAL is a case status of this file, not an
evidence class):

- **EXECUTED_LOCAL (integration)** — every named test exists under exactly that name (`tools/test/evidence.test.mjs` proves
  it on every verify) and PASSED in the evidence bundle of the candidate commit on Windows and on Linux
  (`docs/evidence/b06/`, `tools/evidence.mjs`), each against a real PostgreSQL 17 cluster the test starts itself, and together
  the tests demonstrate the whole expected outcome of the case through product code.
- **PARTIAL** — one criterion for every row (re-check finding N18): a case is PARTIAL when a clause of its registry expectation
  is demonstrated only through a test-bound port (**SIMULATED**, 21 "Evidence classes": a labelled contract fake of a
  collaborator of another package, never of the database), or belongs to a public command or an aggregate another package owns.
  The row lists what is **demonstrated** (EXECUTED_LOCAL evidence of product code), what is **SIMULATED**, and what is **not
  demonstrated in B06** with the package and registry case that own it. A PARTIAL case is not claimed.
- **NOT_APPLICABLE** — a clause the row explains with its reason (a constant of an aggregate B06 does not store, a registry
  verification clause of another package's domain); never a skipped test counted as passed.

No case is PASS by being listed (reference/ACCEPTANCE_SCENARIOS "Execution record"); acceptance is the construction service's
independent review. The durable part of the execution record of 21 is the evidence bundle of each candidate commit and
platform (`docs/evidence/b06/<commit>-<platform>/`, re-check finding N14): the subject (commit and tree), the environment
(node, pnpm, PostgreSQL, operating system), the input manifest (lockfile, migrations, registry, OpenAPI document, matrix and
this file, by SHA-256), the presealed expected truth (this file's case rows — status, cited tests, what a sealed check observes
— hashed and written before any suite runs), the actual results (a JUnit report per suite, each command's exit status and
times, every cited test of every case with its outcome) and the SHA-256 of every file of the bundle. External effect identity
does not apply to B06 (no case performs an external effect) and the independent review is the service's.

Where the tests live, and why:

- **Command-level cases live in `apps/api/test/`.** They go through the real HTTP route (Fastify `inject`), the real
  composition root (`openDatabase` → `assembleApi`: the api's own verified pool on the temporary cluster, the `pg` unit of
  work, the shipped authorizer, admission limiter and handlers, the closed contract validator and the response guard that
  checks every reply) and a real PostgreSQL 17. A command test that called a handler directly would not observe the admission
  order of manual 10, the problem translation, the authentication step or the answer's bytes, and `packages/persistence` may
  not depend on the api entrypoint (`architecture.rules.json`), so the earlier plan of `packages/persistence/test/commands/`
  was dropped. The fixture is `apps/api/test/support.ts`: the superuser oracle reads every table across tenants; hold points
  inside the unit of work (`journal.reserved`, `journal.commit`, `collaborator`, `after.commit`) fix interleavings
  deterministically, the second request being observed waiting on its lock in `pg_stat_activity` (a wait that never happens
  throws, and the held request is let go in a `finally`); concurrent writers of other roles are real transactions
  (`apps/api/test/writers.ts`); no sleep synchronizes anything. Every fixture writes as the role that owns the write and walks
  the listed edges: members are invited and accept (version 2), revisions are sealed through their states, plans are walked to
  VALIDATED with the receipt recorded by the validator's role, step-up proofs are recorded by the verifier's role.
- **Structural and database-level evidence lives in `packages/persistence/test/`** (migrations, RLS, constraints, triggers,
  adapters, journals, leases, the last-owner race, the integrity guards, the security-fact streams) **and
  `packages/application/test/`** (contracts, schemas, admission, the response schemas, the approval-hash golden vector).
  Database-level case tests drive the product's adapters (PgPlanRepository, PgCommandJournal, PgRequestJournal, PgLeaseStore) on
  real connections of the runtime roles; raw SQL appears only for the database facts beneath them.
- **Oracles are independent of the code under test** (21 "Independent oracles"): the approval hash is recomputed by a function
  written from reference/HASHING_AND_ACCOUNTING_RULES and pinned to a golden vector derived outside the product; row counts,
  states, events, security facts and journal rows are read by the superuser oracle. Every strengthened test was run against
  the mutation that had survived it (group records), and the integration re-ran the revert proofs on the merged tree (design
  §12d.3).
- What the acceptance tests bind that a deployment of this edition does not (I-INT-2): the plan-side ports ArtifactResolver,
  PlanPatchCompiler and DisclosureComposer (CMD023, CMD025), for CMD026 an ExternalActionInspector that reports the completed
  stages a test registers, and for CMD023 on an APPROVED plan a CommercialConsequenceInspector that reports the unreconciled
  consequences a test registers (the edition binds `noCommercialConsequencesInThisEdition`, D-PLAN-4). They are ports of
  `@kauro/application`, never fakes of the database.

## Command triads

One file per command in `apps/api/test/`, three tests named after the registry cases (CMD025-OK adds the golden vector of
`packages/application`; the review added tests beside them, cited in the rows). Every RACE row covers the three elements of
its registry scenario — identical retry, conflicting same-key request, crash at the intent/commit boundary — in its own test;
`apps/api/test/idempotency.test.ts` repeats the conflict, the replay, the lost response and the concurrent duplicate for all
seven commands (S052 row). Every denial is a durable security fact (D-FACT-1): in the agency's stream for a proven member, in
the prober's own identity stream (`agency_id` NULL) for a non-member, anonymous for a request without a subject.
