# B09 — case map

Every case of package B09 (registry `cases.json` / `additional_scenarios.json`; gates G-PAYMENT and G-FISCAL_LOCAL; `node
tools/package-brief.mjs B09`) mapped to the tests that demonstrate its expected outcome, to what a sealed check observes, and to
the packages the rest of it depends on. Design: `docs/design/B09-payments-fiscal.md`. This is the design-time map of branch
`b09/design`: the tests that exist on this branch are cited as they are; the command-level tests are the implementation
mandates' deliverables and are named here by file and exact title, so the implementation writes them under exactly these
names and the B06 evidence tooling (`tools/evidence.mjs`, extended by M3 to read this file) can prove every citation resolves.

Status vocabulary (21 "Evidence classes"; every claim names its class):

- **EXISTS** — the cited test is on this branch and passes in `pnpm run verify` against a real PostgreSQL 17 cluster it starts
  itself (database level) or as a pure unit (domain arithmetic and rules). It demonstrates the clause named, not the whole case.
- **PLANNED (Mn)** — the command-level test the mandate Mn writes: through the real route (Fastify `inject`), the composition
  root, the `pg` unit of work, the shipped authorizers and handlers, the response guard and a real PostgreSQL 17, like the B06
  command tests (`apps/api/test/`). Hold points and waits observed in `pg_stat_activity` fix interleavings; no sleep.
- **SIMULATED** — a clause shown through a labelled contract fake of the payment provider, the webhook verifier, the evidence
  store, the fiscal bridge or the service authenticator (`integrationClass: "CONTRACT_FAKE"`, D-FAKE-B1). Never counted as
  integration; the real provider evidence is B15's (G-PAYMENT live: B15/B19). A case with a SIMULATED clause is **PARTIAL** at
  closure, with the demonstrated half named.
- **LATER (Bnn)** — a clause another package owns, with the registry case that owns it.

The registry verification clause of every B09 case is the same: "Separate submitted, uncertain, captured, issued and
bank-available facts; never grade from a screenshot." Every sealed check below therefore reads durable rows through the
superuser oracle — attempt, order, capture, authorization, refund, document, ledger and settlement rows, events and journal
entries — never a browser state, a provider dashboard or a screenshot; and each names which of the five facts it observes.

## Gates

- **G-PAYMENT** (manual 15; evidence rule "Exact subject, public consumer, independent truth, complete result, meaningful negative
  control and reviewer acceptance"): B09 demonstrates the local contract — every case's durable facts on a real database with
  labelled provider fakes. The live half (a legitimate payment captured, reconciled, refunded on the real merchant account) is
  B15's integration and B19's activation, and needs the owner's merchant/KYC action (the brief's owner action).
- **G-FISCAL_LOCAL** (manual 15): R2-128 and the local fiscal boundary are demonstrable here (the bridge's `prepare` and the
  database's validation guard); issuance itself (CMD035, R2-082..R2-084) is B15's and needs the owner's fiscal identity, the
  numbering authorization and the issuance entitlement.
