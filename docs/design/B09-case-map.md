# B09 — case map

Every case of package B09 (registry `cases.json` / `additional_scenarios.json`; gates G-PAYMENT and G-FISCAL_LOCAL; `node
tools/package-brief.mjs B09`) mapped to the tests that demonstrate its expected outcome, to what a sealed check observes, and to
the packages the rest of it depends on. Design: `docs/design/B09-payments-fiscal.md` (revised after the adversarial review; its
§16 "Critique record" names the finding each critique test answers). It began as the design-time map of branch `b09/design` and
is kept on the implementation branches: since the stage-1 integration (`b09/impl-stage1`, the merge of M1 and M2) every row opens
with its closure status at that stage; the tests that exist on the branch are cited as they are; the command-level tests are the implementation mandates' deliverables and are
named here by file and exact title, so the implementation writes them under exactly these names and the B06 evidence tooling
(`tools/evidence.mjs`, extended by M4 to read this file) can prove every citation resolves. `tools/test/b09-case-map.test.mjs`
proves on every verify that every B09 case has one row, that every cited existing test exists under exactly its title, and that
every DENY and RACE row of CMD028–CMD034 states its registry scenario (D-CASEMAP-B1).

Closure status of a case (the first word of every status cell; `tools/test/b09-case-map.test.mjs` checks it on every verify), recorded
at the stage-1 integration as `(stage 1: …)` and restated by the stage-2 mandate that demonstrates the row under its own label —
`(stage 2, M3: …)`, `(stage 2, M4: …)`, `(stage 2, INT-2: …)`:

- **EXECUTED_LOCAL** — every clause of the registry expectation is demonstrated by the cited tests, each on the branch and passing in
  `pnpm run verify` on Windows and on Linux at the head of `b09/impl-stage1`; no planned or simulated clause remains.
- **PARTIAL** — the cited tests on the branch demonstrate the clauses named (the database, domain and adapter halves), and the row
  names what remains with the stage-2 mandate or later package and the case that owns it (`remaining: …`). A PARTIAL case is not
  claimed.
- **MISSING** — no test of the case runs at this stage; the row states the reason and the stage-2 mandate and case that deliver it.

A stage-2 mandate that writes a cited test moves its row (M3, M4, INT-2) and restates its status under its own label; the check
refuses a MISSING row that cites a test on the branch and an EXECUTED_LOCAL row that cites one that is not. A row whose every clause
runs through the routes and a real database but whose provider-side facts come from a labelled contract fake stays PARTIAL, with the
live integration (B15) as what remains.

Evidence classes of the cited tests (21 "Evidence classes"; every claim names its class):

- **EXISTS** — the cited test is on this branch and passes in `pnpm run verify` against a real PostgreSQL 17 cluster it starts
  itself (database level, through the runtime login roles) or as a pure unit (domain arithmetic and rules). It demonstrates the
  clause named, not the whole case.
- **PLANNED (M3 / M4 / INT-2)** — the command-level test the stage-2 mandate M3 (the payment service's side) or M4 (the request
  side) writes, or — for a scenario that crosses both — the stage-2 integrator (INT-2; design §14, D-STAGE-B1): through the real
  route (Fastify `inject`), the composition
  root, the `pg` unit of work, the shipped authorizers and handlers, the response guard and a real PostgreSQL 17, like the B06
  command tests (`apps/api/test/`). Hold points and waits observed in `pg_stat_activity` fix interleavings; no sleep. A crash is
  injected at a named boundary by a hold point that ends the process's unit of work without its commit (the B06 technique).
- **SIMULATED** — a clause shown through a labelled contract fake of the payment provider, the webhook verifier, the evidence
  store, the fiscal bridge, the service authenticator, or — until their package is on main — the platform ports of B07 (source
  availability and lineage) and B08 (delivery capacity) (`integrationClass` / `binding` `CONTRACT_FAKE`, D-FAKE-B1). Never counted as
  integration; the real provider evidence is B15's (G-PAYMENT live: B15/B19). A case with a SIMULATED clause is **PARTIAL** at
  closure, with the demonstrated half named.
- **LATER (Bnn)** — a clause another package owns, with the registry case that owns it.

The registry verification clause of every B09 case is the same: "Separate submitted, uncertain, captured, issued and
bank-available facts; never grade from a screenshot." Every sealed check below therefore reads durable rows through the
superuser oracle — attempt, order, capture, authorization, refund, document, ledger and settlement rows, events and journal
entries — never a browser state, a provider dashboard or a screenshot; and each names which of the five facts it observes.

The registry scenario of every DENY triad is "Foreign tenant/wrong role and then one missing material prerequisite", of every RACE
triad "Identical retry, conflicting same-key request and crash at the intent/commit boundary" (cases.json); the planned titles
below name each element (10 "Contract tests and compatibility": wrong role, wrong agency, stale version, duplicate request,
changed-body same key, lost response, external uncertainty).
